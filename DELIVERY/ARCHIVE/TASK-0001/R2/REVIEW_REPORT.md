## 2. 必须修订的问题

### R2-01｜高：JSON 示例与 Schema 定义不一致，且引用和统计无法自洽

方案第 3.1 节把设备集合定义为 `deviceCatalog.devices[]`，但第 3.2 节 JSON 示例把 `devices` 放在顶层。示例中的传感器引用 `deviceId = dev-synth-cpu`，但示例设备列表中不存在该 ID。完整性统计还声明枚举 3 台设备、物理 1 台、虚拟 1 台、隐藏/历史 1 台，但实际只列出 1 条设备记录；诊断计数中出现的 Normal、Unavailable、Unknown 也无法从示例中的记录完整对应。

**要求：**
1. 统一 Schema 和 JSON 示例的正式结构，设备集合必须放在同一个约定位置。
2. 修复所有跨对象引用，示例中每个 sensor/device/driver/rawEvidence 引用必须能解析，或明确标为省略的外部对象。
3. 让设备数量、分类数量、状态计数与示例对象逐项一致；若计数按采集项而非设备统计，必须在字段名或说明中明确统计粒度和分母。
4. 保留纯合成数据，并再次执行 JSON 语法和语义一致性校验。

### R2-02｜高：空事件查询结果被错误映射为设备正常

方案第 4.1 节规定，`ReliabilityEventCollector` 查询成功但结果为空时，按 0 条 `Success + Normal` 处理。该规则把“在指定日志通道和时间窗口内没有查到事件”误解成“设备健康正常”。事件缺失只能说明本次查询没有返回事件，不能证明硬件、驱动或系统不存在问题。

**要求：**
1. 采集执行状态可以是 `Success`，但诊断结论不得仅因事件列表为空就自动设为 `Normal`。
2. 明确空结果的语义，例如记录 `Success` + `Unknown`（或另行提出不误导的中性表达，但不得擅自扩充已确认枚举）。
3. 只有存在足够、适用且有依据的诊断证据时，才允许生成 `Normal`。
4. 增加空日志、日志通道不可访问、查询窗口内无事件、日志保留不足等合成测试场景。

### R2-03｜中：四桶设备分类声称互斥，但隐藏与历史断开条件可能重叠

方案第 1.1 节把 `HiddenOrNonPresent` 和 `HistoricalDisconnected` 定义为互不重叠的桶，但两者都涉及 `isPresent == false`。当前文字没有给出优先级、判别来源或可重复执行的分类算法。Windows 设备管理器中显示的非在位/隐藏设备可能同时具有历史断开属性。

**要求：**
1. 定义明确的分类优先级与判定算法，说明每一桶使用哪些可观测字段/接口。
2. 无法可靠区分隐藏设备与历史断开设备时，应允许落入明确的 Unknown/Unclassified 类别或保留原始属性，不得强行归类。
3. 明确四桶互斥的实现依据，并补充重叠输入、信息不足和重复枚举的合成测试。

### R2-04｜中：Partial 状态和双轴聚合规则不完整

方案定义了 7 种 `CollectionStatus` 和 7 种 `DiagnosticFinding`，但示例映射没有明确说明 `CollectionStatus = Partial` 时如何表达诊断结论。文中也没有清晰定义整次扫描、采集器、设备、数据项四个层级的状态聚合规则；不能只写“分层使用”，否则实现方可能自行推导出不同规则。

**要求：**
1. 为 `Partial` 给出明确规则和至少一个成功/失败混合的示例。
2. 定义每个层级的状态归属、聚合方式和禁止的推断；尤其不能因某个数据源成功而把设备整体判为 Normal。
3. 说明 `CollectionCompleteness` 的计数粒度、分母、重复项处理和状态计数之间的关系。

### R2-05｜中：7×7 状态组合测试要求无法直接执行

测试矩阵写有覆盖“全部 7×7 关键组合”，但方案没有给出组合期望表或可推导的映射规则。测试执行者无法据此判断每个组合应接受还是拒绝。

**要求：**
给出 7×7 组合规则表，或明确哪些组合合法、哪些组合不可能、哪些组合必须降为 Unknown/Unavailable，并为每类给出断言。若不打算测试全部 49 种组合，应修正“全部 7×7”的表述并列出实际覆盖集。
