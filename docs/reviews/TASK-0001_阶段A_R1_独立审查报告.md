## 3. 必须修订的事项

### R1-01｜完整 PnP 设备覆盖的架构落位不足

R1 将 Phase 1 采集脚本描述为“9 类首轮采集”，并把完整设备类别扩展放在后续阶段。垂直切片可以分批实现，但架构必须从第一版就定义通用 PnP 设备枚举模型、设备身份、设备实例路径、硬件/兼容 ID、Problem Code、当前/隐藏/历史/虚拟设备分类，以及逐设备采集结果的扩展方式。不得把设备类别固定为不可扩展的九个静态分类。

### R1-02｜采集执行状态与诊断结论必须双轴建模

正式需求已要求采集执行结果与诊断结论分开存储。R1 Schema 不能仅依赖单一 CategoryStatus 表达“采集成功”与“设备健康正常”。修订方案必须分别定义：
- Collection/Acquisition Status：Success、Partial、Unsupported、Unavailable、PermissionDenied、Failed、Skipped 等；
- Diagnostic Finding：Normal、Abnormal、Warning、CollectionFailed、Unsupported/Unavailable、Unknown 等。

必须说明类别、设备、数据项和传感器读数各层级如何表达这两类状态，避免把读取成功直接当作硬件正常。

### R1-03｜完整证据数据模型和 Schema 演进策略不足

修订方案必须说明 Schema 如何容纳：
- 全量设备记录及其身份/父子关系/接口与总线位置；
- 驱动元数据和设备问题代码；
- 传感器读数、单位、来源、时间戳、有效性和阈值依据；
- SMART/NVMe 等健康信息及其支持状态；
- 系统事件原始字段、事件来源、时间范围和关联证据；
- 采集缺口、错误、警告、原始输出引用和完整性统计；
- 未来新增采集器时的兼容和版本迁移策略。

不得为了首个垂直切片把正式 Schema 设计成只能容纳少数固定类别的结构。

### R1-04｜Diagnostics 与 Reporting 的边界需要按最终产品重新论证

可以分阶段实现，不要求 Phase 1 一次完成全部功能。但方案必须定义长期模块边界和依赖方向：
- Diagnostics：系统事件、WHEA、BugCheck、WER/RAC、异常重启、设备错误证据规范化与关联；
- Reporting：JSON、XLSX、HTML、AI 分析说明和 ZIP 组装；
- Reporting 只能消费已采集/已规范化的数据，不得启动扫描；
- XLSX/ZIP 所需依赖、许可、体积、维护性和测试策略需要列出候选方案及取舍，不得未经决策引入依赖。

### R1-05｜导出与隐私门禁必须覆盖整个报告包

R1 主要描述原始 JSON 导出提示。最终报告包包含设备硬件 ID、序列号（如可读）、MAC/IP、用户名/路径、事件消息等潜在敏感信息。修订方案必须定义 ZIP 导出前的统一隐私提示、报告内容预览/范围说明、用户取消时不弹出保存框且不写文件，以及原始证据与可选脱敏分享副本的边界。

### R1-06｜采集完整性与“全部汇报”原则需要落到结构设计

必须设计设备枚举完整性和数据项覆盖统计，区分：
- 不支持；
- 不可用；
- 权限不足；
- 采集失败；
- 数据无效/可疑；
- 已成功采集但未形成健康结论；
- 明确异常与警告。

所有缺口必须有来源、原因和影响范围；不得把未采集/无法读取显示为正常，也不得仅因读取失败就断言硬件损坏。

### R1-07｜测试矩阵需要覆盖完整产品的长期边界

在保留 Phase 1 最小测试的前提下，补充后续测试边界：合成 PnP 设备集合、重复/父子设备、隐藏和历史设备分类、Problem Code 映射、传感器无效/离群数据、SMART/NVMe 能力差异、事件时间线、Schema 兼容、XLSX 工作表与行数一致性、HTML/ZIP 内容完整性、隐私取消门禁、AI 说明完整性。明确哪些属于 Phase 1 必测，哪些属于后续阶段。
