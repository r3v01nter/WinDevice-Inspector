# AI 交付操作手册

> 本手册规定 Gemini 网页端、Antigravity 和 ChatGPT 在 WinDevice-Inspector 仓库中的实际交接方式。项目负责人只负责下载 Gemini 产物、放入本地暂存区，并在需要 ChatGPT 继续时发出明确口头指令。

## 一、固定分工

| 角色 | 主要职责 | 禁止事项 |
|---|---|---|
| Gemini 网页端（Neon / Hydrogen 等可用强模型） | 主要代码生产；复杂模块、测试、重构和技术说明；按任务书输出完整文件 | 不直接推送仓库；不擅自改变任务范围或正式架构决定 |
| Antigravity（当前可用 Gemini 3.8） | 本地文件操作、交付检查、打包、应用文件、Git 分支提交和推送、编译测试、收集日志 | 不重新设计核心架构；不擅自扩大范围；不推送 main；不自行合并 PR |
| ChatGPT | 项目总控、任务书、技术决策协调、独立审查、返工要求、仓库文档与任务状态维护 | 未收到项目负责人明确的“继续/审查/推进”指令时，不自动开始下一阶段 |
| 项目负责人 | 下载 Gemini 输出、放入暂存目录、启动 Antigravity；决定何时让 ChatGPT 继续；最终验收 | 不需要手动解压、整理、复制、Git 提交或推送 |

## 二、固定文件流

1. ChatGPT 在仓库发布一份独立任务书，明确目标、基准 SHA、文件范围、验收标准和停止门禁。
2. 项目负责人把任务书交给 Gemini 网页端。
3. Gemini 生成完整文件，并提供完整文件清单、测试说明和完成回执。大批文件可按完整目录结构打包为 ZIP。
4. 项目负责人下载 Gemini 的文件，放入本地仓库克隆中的：

   `DELIVERY/LOCAL_STAGING/待上传/`

5. 项目负责人打开 Antigravity，要求它读取本手册和当前任务书，处理暂存区文件。
6. Antigravity 检查文件清单、路径、重复文件、压缩包安全性、任务范围和基准版本；不确定或冲突时停止并报告。
7. Antigravity 创建独立交付分支，将交付文件放入规定位置，生成交付清单，执行任务书要求且环境允许的检查，然后提交并推送分支。
8. Antigravity 把分支名、commit SHA、推送结果、文件清单、检查结果和未完成项报告给项目负责人。
9. 项目负责人确认交付已推送后，自己口头通知 ChatGPT“检查 TASK-XXXX 的交付”或“继续下一步”。
10. ChatGPT 才开始读取远端分支、独立审查或推进下一步。未收到该指令，不自动审查、不自动进入下一阶段。

## 三、本地暂存区规则

- 唯一本地暂存路径：`DELIVERY/LOCAL_STAGING/待上传/`。
- 此路径仅用于本机中转，已加入 Git 忽略规则，不会作为项目内容提交。
- 用户可把 Gemini 下载的 ZIP 或完整文件直接放入该目录；不要求用户自行解压、改名或拆分。
- Antigravity 负责解压和整理，但必须先检查 ZIP 路径穿越、绝对路径、重复文件、超出任务范围的文件及可疑二进制。
- 不得把暂存区中的所有内容不加区分地复制进仓库。
- 不得提交密钥、访问令牌、浏览器数据、个人文件、真实设备扫描数据、日志中的敏感信息或本机配置。
- 暂存区处理成功后，可将已处理文件移入本地备份/清理；不得静默删除唯一副本。先确认远端分支提交可读取，再按任务书保留或清理本地暂存文件。

## 四、Git 分支与提交规则

- 每个任务/交付轮次使用独立分支，建议命名：`delivery/TASK-0001-R2`。
- 分支必须从任务书指定的基准提交或当前确认的任务基线创建；如果远端基线已变化，先核对差异，不能盲目覆盖。
- Antigravity 只推送交付分支，不直接推送 `main`，不强制推送，不重写公共历史。
- 同一轮次重复上传时，先检查远端分支现状；不得覆盖或删除已提交的原始交付。修订必须使用新轮次/新分支，例如 R3。
- 交付文件放在 `DELIVERY/INBOX/待交付/` 的平面入口，保留原始文件名和内部相对目录结构；不得创建任务专属子目录。
- 代码任务若任务书要求在分支中应用源码，Antigravity 可按任务书把源码放到 `src/`、测试放到 `tests/`，同时在交付清单中逐项列明；所有变更仍只存在交付分支，等待 ChatGPT 审查。
- Antigravity 可以创建 PR 供审查，但不得自行合并。若当前环境不能创建 PR，推送分支并报告即可。
- 提交信息格式建议：`delivery(TASK-0001-R2): upload reviewed package`。
- 推送后必须核验远端分支 HEAD 与本地提交 SHA 一致。

## 五、Antigravity 每次执行前必须做的检查

1. 确认仓库根目录和当前仓库名是 `WinDevice-Inspector`。
2. 读取本手册、任务中心当前任务和对应独立任务书。
3. 确认本次任务 ID、轮次、基准 SHA、允许文件范围和禁止事项。
4. 列出暂存区所有输入文件；ZIP 先列目录，不直接盲目解压。
5. 检查文件名冲突、路径异常、超范围文件、敏感信息和空文件。
6. 对每个交付文件记录源文件名、目标仓库路径、大小和 SHA-256（可用时）。
7. 若任务范围、基线或目标路径不明确，停止并报告，不猜测。
8. 完成后核验 Git diff、提交内容、远端分支和 commit SHA。

## 六、Antigravity 完成回执必须包含

- 任务 ID、轮次、基准 SHA、交付分支。
- Gemini 输入文件清单及 SHA-256（可用时）。
- 仓库新增/修改文件清单。
- ZIP 解压与路径安全检查结果。
- 实际执行的命令、环境、退出码。
- build/test 的真实结果；未执行必须写 Not run。
- commit SHA、远端分支 URL、PR URL（如有）。
- 未处理文件、冲突、偏离任务书的事项和风险。
- 明确声明：没有推送 main、没有合并 PR、没有删除历史交付。

## 七、ChatGPT 的人工触发门禁

Antigravity 推送完成不代表任务已审查或验收。ChatGPT 不应仅因为仓库出现新分支就自动推进。

项目负责人可使用自然语言明确触发，例如：

- “TASK-0001 R2 已上传，检查交付分支。”
- “继续下一步，审查刚才 Antigravity 上传的内容。”
- “审查通过后，给我下一阶段任务书，但先不要开始编码。”

ChatGPT 收到指令后，先核对分支、SHA 和文件清单，再按任务书审查。是否合并、是否更新 main、是否进入下一阶段，仍受任务书门禁和项目负责人的明确批准约束。

## 八、绝对禁止

- 直接向 `main` 推送 AI 生成的未经审查变更。
- 强制推送、删除远端分支、覆盖历史交付或擅自合并 PR。
- 将本地暂存区、真实扫描数据、凭据或个人文件整体上传。
- 将“文件已上传”表述为“审查通过”或“验收通过”。
- 在项目负责人尚未明确要求 ChatGPT 继续时，自行触发下一阶段。
