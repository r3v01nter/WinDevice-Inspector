# 任务创建与推进规范

> 本文件是 WinDevice Inspector 长期任务管理规则。新窗口、新会话或更换 AI 执行方时，以本规范和任务中心索引为项目管理依据，不依赖旧聊天记录。

## 1. 目的与适用范围

本规范统一管理软件功能开发、缺陷修复、技术调查、架构工作、文档整理和仓库治理任务。

目标是让项目负责人只需打开任务中心，就能知道：

- 现在正在做什么；
- 当前任务书在哪里；
- 任务由谁执行、交付什么；
- 工作推进到哪个阶段；
- 已经完成什么、还有什么未完成；
- 交付放在哪里、由谁审查；
- 哪些内容已经验收，哪些仍未验证。

## 2. 唯一入口与文件职责

| 文件/目录 | 唯一职责 |
|---|---|
| `任务中心/README.md` | 任务管理总入口和导航 |
| `任务中心/当前任务.md` | 唯一当前处理项指针，直接链接当前任务书 |
| `任务中心/任务索引.md` | 所有任务的状态、负责人、任务书、交付和审查入口 |
| `任务中心/审查索引.md` | 每轮审查、验证和验收结果 |
| `任务中心/开发变更记录.md` | 已实际合入的正式变更 |
| `任务中心/任务创建与推进规范.md` | 本文件：任务如何创建、执行、交付、审查和关闭 |
| `docs/tasks/` | 每个任务一份完整、独立的任务书 |
| `docs/templates/` | 可复用任务书、完成回执、审查报告和缺陷模板 |
| `DELIVERY/INBOX/待交付/` | 唯一平面交付入口 |
| `DELIVERY/ARCHIVE/` | 按任务编号和轮次保留原始交付与审查报告 |
| `docs/reviews/` | 必要时存放跨轮次审查资料或本机验证记录 |
| `docs/issues/` | 已确认缺陷及复验记录 |

不要为同一个职责再建立第二份“当前任务表”或平行交付入口。若摘要文件与任务中心状态不同，以任务中心当前指针和索引为准；发现冲突应修正摘要，不应维护两套状态。

## 3. 任务分类与编号

任务编号必须稳定、唯一，不因返工或换执行方而改变。

| 类型 | 编号建议 | 适用场景 |
|---|---|---|
| 软件实现 | `TASK-0001` 起 | 功能、模块、界面、基础设施 |
| 缺陷修复 | `BUG-0001` 起，或纳入所属 TASK | 有明确复现和修复范围的问题 |
| 技术调查 | `SPIKE-0001` 起 | 需要验证技术可行性、性能或兼容性 |
| 仓库/流程治理 | `WDI-AUDIT-0001` 等 | 目录、文档、协作流程和项目管理 |
| 紧急问题 | 使用原任务编号并标记优先级 | 不另造临时平行任务状态 |

已有编号保持不变。R1、R2、R3 是同一任务的不同交付/返修轮次，不是新任务。只有工作目标和验收边界发生实质变化时，才创建新任务并在索引中建立关联。

任务书文件名优先中文并保留编号，例如：

- `TASK-0002_设备扫描流程实现.md`
- `BUG-0003_扫描取消后子进程未退出.md`
- `SPIKE-0001_PowerShell兼容性验证.md`
- `WDI-AUDIT-0001_R3_返修任务书.md`

## 4. 任务书必须自包含

**任务书是执行方的主要工作输入。执行方下载一份任务书后，应能理解背景、目标、范围、约束、操作要求和交付标准，不应被要求先遍历整个仓库或翻找聊天记录。**

每份正式任务书必须包含：

1. 任务身份：编号、名称、轮次、状态、优先级、负责人、执行方、发布日期。
2. 项目背景：只写理解本任务所必需的项目背景。
3. 当前基准：基准日期、目标分支、完整 commit SHA（可取得时）。
4. 当前事实：已确认事实、现有实现、已知问题和前置条件。
5. 权威规则：将本任务必须遵守的产品/架构约束直接摘录或总结在任务书中。
6. 工作目标：完成后应出现什么可观察结果。
7. 工作范围：允许新增、修改、删除的文件或模块。
8. 非目标：本轮明确不做什么。
9. 操作步骤：按可执行顺序描述，避免只给抽象目标。
10. 验收标准：逐条可核验，说明对应证据。
11. 测试要求：命令、环境、测试场景和证据格式。
12. 交付要求：完整文件清单、目录组织、完成回执和交付方式。
13. 风险与待决策事项：区分已决定、建议、未知和需要负责人批准的事项。
14. 停止条件：完成本任务后不得擅自推进的下一阶段。

### 4.1 资料引用与访问要求

- 把执行任务真正需要的背景和规则写入任务书，不要只给一长串“请先阅读”链接。
- 对必须依赖仓库现状的工作，列出精确文件路径和需要核验的字段/区域。
- 对纯文档任务，原则上直接提供必要事实、摘录和审查问题；除非文件本身是修改对象，不要求全面浏览仓库。
- 对代码任务，执行方只需先读取任务书指定的相关源码、接口、测试和决策文件，再检查与任务直接相关的依赖；不得无目的遍历整个仓库。
- 明确区分“背景参考”与“开始工作前必须核验”的文件。
- 任务书记录基准 SHA 和日期。若执行方发现相关文件在基准之后变化，只核对与本任务有关的变化，并在回执中说明。
- 如果必要资料无法在任务书中准确提供，必须列为明确前置条件；不能让执行方猜测。

### 4.2 独立任务书的质量标准

项目负责人应当可以把任务书单独转发给 Gemini。Gemini 不应需要：
- 询问“项目是什么、当前做到哪一步”；
- 翻阅其他聊天窗口；
- 自行猜测哪些决定已经批准；
- 从几十个文件中寻找真正的任务要求；
- 自行设计交付格式或验收口径。

必要的源代码、二进制、设计素材或大型资料仍可作为单独附件，但任务书必须说明附件清单、用途和缺失时的处理方式。

## 5. 任务创建流程

1. **确认需求**：明确要解决的问题、预期结果和提出者。
2. **检查现状**：由 ChatGPT 检查任务中心、相关文档、已有实现、未决事项和相邻任务，避免重复建设。
3. **确定任务边界**：拆分目标、非目标、允许修改范围和风险。
4. **处理决策依赖**：涉及产品/架构未决事项时，先向项目负责人提出；未经批准不得将假设写成决定。
5. **编写自包含任务书**：使用中文任务书模板，补齐上下文、执行步骤、验收和交付规范。
6. **质量检查**：检查路径、状态、SHA、链接、文件清单、验收标准是否一致。
7. **发布到仓库**：保存到 `docs/tasks/`，更新当前任务指针（若成为当前任务）和任务索引。
8. **交给负责人确认**：项目负责人打开/下载任务书，决定是否交给 Gemini 开始执行。

未达到可执行条件的任务保持“待规划”，不要为了推进而伪造完整任务书。

## 6. 任务推进状态机

标准状态：

`待规划 → 待生产 → 生产中 → 待交付 → 审查中 →（通过）待本机验证 → 验收通过 → 已归档`

返工分支：

`审查中 → 返工中 → 待交付 → 审查中`

文档任务等不需要本机验证的工作，可由审查通过进入“待负责人验收”，再进入“验收通过”。可根据任务性质标记“不适用”，不能为了状态完整而制造测试。

| 状态 | 含义 | 进入条件 | 退出条件/责任方 |
|---|---|---|---|
| 待规划 | 需求尚不完整 | 刚提出或存在关键未知 | ChatGPT 补齐范围或向负责人提问 |
| 待生产 | 任务书完整，可开始执行 | 任务书发布且前置条件满足 | 负责人决定启动 |
| 生产中 | 执行方正在工作 | 负责人已交办 | Gemini 完成自检并交付，或报告阻塞 |
| 待交付 | 产出已完成，尚未进入收件箱 | 完成回执和文件包准备好 | 负责人检查并上传 |
| 审查中 | 交付已进入唯一入口 | 负责人通知交付就绪 | ChatGPT 完成独立审查 |
| 返工中 | 审查发现明确问题 | 审查报告列出缺陷和复验标准 | 新轮次修订任务书/要求明确后重新生产 |
| 待本机验证 | 独立审查通过，仍需目标环境测试 | 代码/硬件/平台验证适用 | 负责人提供真实测试证据 |
| 待负责人验收 | 所有适用技术门槛已通过 | 审查通过，验证完成或不适用 | 负责人明确批准或要求补充 |
| 验收通过 | 负责人已明确批准 | 具备所有适用证据并收到批准 | 进入归档 |
| 已归档 | 原始交付、审查和结果已保存 | 归档核验完成 | 作为历史记录保留 |

特殊状态：已暂停、已取消、被其他任务替代。必须记录原因、日期和关联任务。

### 6.1 当前任务指针规则

- `当前任务.md` 只保留一个当前处理项。
- 一个任务的生产、交付、审查和返工期间，它持续是当前处理项。
- 只有当前任务关闭、暂停或负责人明确切换后，才切换指针。
- 下一项任务只出现在任务索引的“待生产/后续”状态，不得提前冒充当前任务。
- 每次状态变化都同步任务索引；审查结论同步审查索引；实际合入变更才写开发变更记录。

## 7. Gemini 生产规则

- Gemini 以当前任务书为执行契约；更高优先级的正式产品/架构决定仍然优先。
- 先读任务书，再按任务书列出的精确路径做必要核验。
- 不做与任务无关的大范围仓库探索。
- 不擅自扩大范围、改产品决定、增加依赖、变更公开数据契约或修改无关文件。
- 遇到任务书冲突、缺少关键输入或需要新决策时，暂停受影响部分并报告，不自行猜测。
- 不直接提交/推送 GitHub；标准流程是把完整文件交给项目负责人。
- 不得声称执行了未执行的命令、测试或构建。

## 8. 交付、审查与返工

### 8.1 唯一交付入口

项目负责人检查 Gemini 返回文件后，将本轮所有交付文件直接放进：

`DELIVERY/INBOX/待交付/`

这是平面收件入口。不得要求项目负责人预先创建任务编号子目录、拆包、改名或重组。完整文件的内部相对目录结构可以保留，但收件目录本身不增加任务专属层级。

### 8.2 独立审查

ChatGPT 按任务书逐条检查：
- 文件是否齐全、是否可读、内容是否完整；
- 是否满足目标、范围、非目标和产品约束；
- 是否存在错误、遗漏、未经批准的变更；
- 测试、构建、运行声明是否有证据；
- 是否正确处理隐私、安全、异常和边界情况；
- 文档、代码、测试和回执是否一致。

审查报告必须列出证据、问题严重度、影响、返修要求和复验标准。

### 8.3 返工轮次

- 每轮交付独立编号 R1、R2、R3……
- 旧轮次原始文件只读保留，不覆盖。
- 返工任务书/修订要求应直接写明尚未解决的问题，不要求 Gemini 自己重新推断。
- 若返工要求足够明确，可在任务书中附上完整问题清单和必要上下文。
- 每轮结束后更新任务索引、审查索引和归档说明。

## 9. 验证与验收门槛

分别记录以下四个概念，不得混用：

1. **生产完成**：执行方认为工作已做完，并提交完整文件。
2. **独立审查通过**：ChatGPT 按任务书检查，当前范围未发现阻断问题。
3. **本机/目标环境验证通过**：项目负责人或有证据的目标环境完成实际构建、运行和测试。
4. **最终验收通过**：项目负责人明确批准。

纯文档任务可以将本机验证标为“不适用”，但仍需独立审查和负责人验收。代码任务不得用静态阅读替代实际构建和运行证据。

## 10. 归档与长期追踪

每轮审查处理完成后：

1. 将本轮原始交付按任务编号和轮次归档。
2. 保存该轮完成回执、文件清单和独立审查报告。
3. 更新任务索引、审查索引和当前任务指针。
4. 更新开发变更记录（仅限已实际合入的正式变更）。
5. 清空待交付入口本轮文件，仅保留 README。
6. 重新读取 GitHub 核验归档文件数量、入口状态和关键链接。

归档不等于验收。被返工的文件也必须完整保留，作为历史证据。

## 11. 项目负责人日常使用方式

项目负责人只需执行以下动作：

1. 打开 [任务中心](README.md)。
2. 在 [当前任务](当前任务.md) 打开或下载当前任务书。
3. 检查任务书，转交 Gemini。
4. 收到 Gemini 的完整文件后自行检查。
5. 将本轮文件直接放入唯一的待交付入口。
6. 告知 ChatGPT 任务编号和交付已就绪。
7. 查看 ChatGPT 的审查报告；如需返工，转交返工要求。
8. 需要本机验证时按任务书执行命令，并把真实结果交回。
9. 明确批准后，任务进入验收和归档。

不要求项目负责人维护额外表格、重复填写状态或自行整理任务目录。

## 12. 新窗口/新会话接续规则

新会话继续项目时，先从本仓库读取：

1. 本规范；
2. `任务中心/当前任务.md`；
3. 当前任务书链接；
4. 任务索引和最近一轮审查报告（如有）。

只需读取当前任务直接依赖的资料，不必从头遍历所有历史文件。当前任务书必须包含执行所需的完整上下文；本规范负责流程，不替代具体任务要求。

## 13. 本规范的变更控制

本规范是项目管理流程，不是产品需求或技术架构决策。修改流程时：
- 说明变更原因和对项目负责人的影响；
- 保留唯一当前任务和单一交付入口原则，除非负责人明确批准变更；
- 更新相关模板、协作说明和任务中心入口；
- 不得仅凭 Gemini 或 ChatGPT 的建议擅自改变负责人已确认的工作习惯。
