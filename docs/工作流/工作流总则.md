# 工作流总则

## 1. 任务生命周期
规划 → 任务书 → 负责人授权 → 能力核验 → 独立实施 → 自检 → 完整交付 → 负责人触发审查 → 独立审查 → 返修任务书（如需）→ 复审 → 归档 → 负责人最终验收。

每个阶段都有明确负责人。没有收到负责人授权，不得开始会改变产品代码、正式需求或阶段状态的工作。

## 2. 角色边界
| 角色 | 应做 | 不应做 |
|---|---|---|
| Gemini 网页端 | 调研、分析、方案比较、创建/修订任务书、解释技术问题 | 默认不修改 Antigravity 正在操作的工作区；不虚构工具执行结果 |
| Antigravity / Gemini 4 Hydrogen Extra High | 读取任务书、独立实施、运行实际可用测试、生成 ZIP 与完成回执 | 不改任务目标或验收标准；不自审为通过；不越权合并或推送 main |
| ChatGPT GPT-6 | 独立核验交付、记录缺陷、提出返修要求、维护审查和归档记录 | 不在未触发时自动推进；不把未验证内容写成通过 |
| 项目负责人 | 授权、提供输入、触发审查、最终验收 | 不需要替 AI 承担未被授权的技术决策 |

任务书可对默认分工作出明确例外，但必须记录执行方、理由和权限边界。

## 3. 任务书最低要求
每份任务书必须自包含，至少包括：
- 稳定任务编号、轮次、状态、任务负责人和执行者；
- 项目背景、当前可验证基线与基准 commit；
- 目标、非目标、允许修改的文件/目录范围；
- 已确认约束、未决问题和禁止事项；
- 有序实施步骤、验收标准和测试命令；
- 交付文件清单、ZIP 结构、完成回执和哈希要求；
- 分支名称、唯一交付入口、停止条件；
- 本机验证要求及未执行项的如实标注。

## 4. 分支和提交规则
- 代码/文档实施任务默认使用任务轮次独立分支，例如 delivery/WDI-DIAG-001-R2。
- 分支从执行时最新 main 创建；任务书中的基准 SHA 仍作为内容审查基准。若 main 变化影响任务内容，先比较并报告。
- 不直接推送 main，不强制推送，不重写历史，不自行合并 PR。
- 分支创建或推送能力不存在时，生成完整本地交付包和操作说明，交由负责人决定下一步。
- 提交后核验远端分支 HEAD 与报告中的 commit SHA 一致。

## 5. 交付与审查状态
- 待交付：实施者已完成自检，准备提交。
- 已提交 / 待审查：文件已进入唯一收件入口，负责人尚未触发审查。
- 审查中：负责人已明确触发，ChatGPT 正在核验。
- 需返修：审查发现问题，等待下一轮任务书与授权。
- 待本机验证：代码审查完成，但目标环境验证仍缺证据。
- 待负责人验收：技术门槛已满足，等待明确批准。
- 已验收 / 已关闭：负责人明确批准并完成收尾。
- 已归档：原始交付和审查记录保存；归档不等于通过或验收。

## 6. 独立审查
ChatGPT 必须基于实际提交、完整文件和可核验测试证据审查。实施者自述只能作为线索，不作为通过证据。审查报告区分代码/文档审查结论、自动化测试执行状态、Windows 本机验证状态和负责人最终验收状态。

## 7. 返修和归档
返修必须建立新轮次，不覆盖旧轮次。审查不通过后：
1. 保存本轮原始交付；
2. 保存审查报告；
3. 由 Gemini 网页端据审查报告生成下一轮返修任务书；
4. 负责人批准后实施者开始下一轮；
5. 复审后更新任务索引和审查索引。

审查收尾时，将本轮原始交付完整归档到 DELIVERY/ARCHIVE/任务编号/轮次/，保留原始文件名和内部目录结构；报告与归档说明一并保存；更新索引；确认收件箱只剩 README 或其他明确保留文件后再结束。
