# 完整设备诊断与报告导出需求

- 文档状态：项目负责人已确认的产品方向基线
- 产品：WinDevice Inspector
- 适用平台：Windows 11 x64（后续按验证结果扩展）
- 文档性质：产品需求；不是当前开发授权，也不代表相关功能已经实现
- 关联文档：[产品需求总表](PRODUCT_REQUIREMENTS.md)、[技术架构](TECHNICAL_ARCHITECTURE.md)、[路线图](ROADMAP.md)

## 1. 产品目标

提供一个用户主动发起的一键完整设备诊断流程。软件应尽可能枚举并检查 Windows 当前可识别的设备，采集操作系统和硬件接口能够提供的设备身份、驱动、运行状态、问题代码、传感器、存储健康和系统故障证据，保留数据来源与原始证据，并生成可供用户查看及直接交给 ChatGPT、Gemini 等 AI 分析的完整报告包。

产品定位是**设备与系统诊断证据采集器、整理器和报告生成器**，不是自动修复工具，也不替代专业电气测试仪器或厂商专用诊断设备。

核心原则：

> 能可靠读取的诊断信息尽可能完整采集并汇报；不能读取、硬件不支持、权限不足、读取失败或数值可疑的项目也必须明确列出原因。不得静默遗漏、伪造数据或把未知当成正常。

## 2. 一键扫描体验

1. 用户主动点击「一键完整扫描」。
2. 软件展示本次采集范围、目的、预计耗时（可估算时）、权限要求和可能包含的敏感信息。
3. 用户明确确认或取消；取消时不得启动任何采集进程。
4. 确认后执行只读采集，展示进度、各类别状态和可取消操作。
5. 各采集器独立执行；单项失败不得丢弃其他成功结果。
6. 完成后生成统一诊断总览、逐设备结果、采集完整性统计和报告包。
7. 用户检查并选择导出位置；软件不得自动上传 AI 服务或云端。

不允许启动时扫描、后台扫描、定时扫描、空闲扫描、自动重试扫描或设备变化后自动扫描。

## 3. 设备枚举范围

### 3.1 当前设备（完整扫描主体）

尽可能覆盖 Windows PnP / Device Manager 可枚举的全部当前设备及设备类别，而非只收集常见核心硬件。至少覆盖：

- 处理器与处理器设备节点
- 显示适配器、GPU、显示器和显示输出相关设备
- 磁盘驱动器、卷、存储控制器、SATA / NVMe / RAID 设备
- 内存模块及可获取的内存控制器信息
- 主板、芯片组、固件、BIOS/UEFI 和系统设备
- PCI、PCIe、ACPI 及其他总线设备
- USB 主控制器、Root Hub、Hub、外围 USB 设备
- 网络适配器、有线/无线网卡、蓝牙及相关设备
- 音频控制器、音频输入/输出设备
- 摄像头、生物识别、打印、扫描、输入设备
- 电池、电源管理及可枚举的电源相关设备
- 其他即插即用设备、未知设备和未正确识别设备

对每个设备尽可能采集：设备类别、友好名称、制造商、硬件 ID、兼容 ID、设备实例路径、父子关系/位置路径、总线类型、当前状态、Problem Code、驱动提供商/版本/日期/INF/签名信息、服务或关联控制器信息，以及可访问的资源和接口信息。

### 3.2 隐藏设备与历史设备

- 当前存在且已枚举的设备是主要诊断对象。
- 已断开/历史设备应单独分类，不能与当前设备混为一谈。
- 隐藏设备应记录其枚举来源和状态；不得仅因其隐藏或曾经连接就判定为故障。
- 软件虚拟设备、系统逻辑设备和非实体设备应单独标注类别，避免误称为物理硬件。
- 设备总数必须说明统计口径，避免重复枚举、父子节点和多个接口造成误读。

### 3.3 接口、总线和连接状态

在 Windows 或设备接口公开数据允许的范围内，尽可能收集 PCI/PCIe、USB、SATA、NVMe、网络、音频、显示等接口与控制器信息，包括设备路径、硬件标识、链路/协商参数、连接状态、控制器关联和错误记录。

不能可靠获得的链路细节必须列为不支持/未知，不得从设备型号推测实际链路状态。

## 4. 硬件状态和传感器数据

尽可能读取设备或受支持接口暴露的实时/快照数据：

- CPU：型号、核心/线程、频率、负载、温度、功耗及可用状态指标。
- GPU：型号、显存、驱动、温度、频率、功耗、利用率及设备状态。
- 内存：容量、模块/插槽信息、频率、可获取时序、可获得的错误/健康证据。
- 主板：型号、芯片组、BIOS、温度、电压、风扇转速及传感器状态。
- 存储：型号、固件、容量、接口、温度、SMART/NVMe 健康信息、介质错误/错误日志（受控制器与驱动支持限制）。
- 网络：适配器状态、连接介质、链路速率、错误/丢包计数（接口支持时）。
- 电源：电池健康与状态（适用时）、主板暴露的电压/电流/功耗传感器。
- 其他设备：其公开接口提供且有诊断价值的状态字段。

传感器数据必须包含数值、单位、来源、读取时间、读取方法、有效性检查结果及适用的参考阈值依据。不得把未经验证的传感器读数当作校准仪器结果。

## 5. Windows 系统与可靠性证据

系统采集重点是与设备、驱动和稳定性有关的诊断证据，不扩展为软件安装清单或系统优化器。至少评估：

- 设备管理器/PnP 问题代码、设备启动/配置失败。
- Kernel-Power、EventLog 等异常关机与重启记录。
- BugCheck、蓝屏停止代码及可访问的转储文件元数据。
- WHEA-Logger：硬件错误来源、严重程度、错误记录和可用的原始数据。
- PCIe、存储、磁盘、文件系统、控制器和设备重置/掉线事件。
- Display/GPU 驱动重置和相关设备事件。
- USB、网络、音频及其他设备相关事件。
- Windows Reliability Monitor / RAC 和 Windows Error Reporting（WER）记录（可用时）。
- 系统启动、关机、异常恢复的时间线及可关联的证据。

必须保留事件提供程序、事件 ID、级别、时间、记录 ID、通道、原始消息和有价值的事件数据。时间接近只能说明相关性，不能自动证明因果关系。Kernel-Power 41 或 EventLog 6008 本身不能证明电源损坏。

默认时间范围应由用户可见且可配置；报告中记录实际查询范围、日志保留限制和访问失败情况。

## 6. 统一诊断状态

设备级和数据项级结果使用统一判定，并保留原始 Windows 状态/错误码：

| 状态 | 含义 |
|---|---|
| 正常（Normal） | 有足够的成功采集证据，且未发现已知问题；不代表硬件绝对无故障 |
| 异常（Abnormal） | 存在明确设备问题代码、启动失败或其他有充分证据支持的问题 |
| 警告（Warning） | 读数可疑、重复断连、错误事件或潜在风险，尚不足以确认硬件故障 |
| 采集失败（CollectionFailed） | 该数据源预期可访问，但本次读取失败；必须给出错误和原因 |
| 无法检测（Unsupported/Unavailable） | 硬件、固件、驱动或操作系统接口未提供该数据，或当前条件不允许检测 |
| 未知（Unknown） | 证据不足，不能可靠判定 |

规则：

- 读取不到不等于硬件损坏，但必须出现在报告中并提示用户。
- 数值超出有依据的安全/规范阈值可判异常；阈值不确定或传感器可信度不足时判警告/未知。
- 不得为追求“全部正常/异常”的二元结果而伪造结论。
- 每个异常/警告必须说明证据、来源、影响范围、判定依据和建议复核方式。
- 不支持、权限不足、读取失败和数据无效必须分别表达，不能合并成“正常”。

## 7. 采集完整性与数据可信度

报告必须提供扫描完整性统计，至少说明：

- 枚举到的当前设备数量、历史/断开设备数量及统计口径。
- 成功读取设备状态数量、明确异常数量、警告数量、未知数量。
- 各类别和数据源成功、部分成功、不支持、不可用、权限不足、失败、跳过的数量。
- 预期采集项目总数、实际成功数、缺失项目及原因。
- 采集开始/结束时间、耗时、应用版本、采集器版本、Schema 版本、系统版本和实际 PowerShell 运行时版本（适用时）。
- 每项数据的来源、采集时间、查询参数/时间范围、单位、有效性和限制。

不得仅用一个“扫描成功”标志掩盖部分失败。扫描总体状态应由各类别结果计算并解释。

## 8. 报告导出

完整报告包采用 ZIP，至少包含：

| 文件 | 用途 |
|---|---|
| 完整诊断数据.json | 规范化的完整结构化数据、原始证据、状态、来源和采集完整性；作为 AI 主要数据输入 |
| 设备状态清单.xlsx | 供人工筛选、排序和审阅的工作簿 |
| 诊断总览报告.html | 人类可读的诊断摘要、异常清单、时间线和详细结果 |
| AI分析说明.md | 自包含的分析任务、字段说明、状态定义、采集范围和限制 |

### 8.1 Excel 工作表建议

- 诊断总览
- 全部当前设备（每个设备一行）
- 异常设备
- 警告设备
- 隐藏/断开/历史设备
- 驱动信息
- 接口与总线
- 硬件传感器
- 系统事件
- 采集失败与无法检测项目
- 采集完整性

Excel 是人工审阅和筛选格式，不替代 JSON 的完整嵌套数据和原始证据。

### 8.2 AI 分析说明

AI 说明必须随报告包一起导出，并要求接收 AI：

- 先检查报告结构、Schema 版本和采集完整性。
- 区分已确认事实、异常证据、警告、假设和未知。
- 不把缺失数据解释为正常，也不把不支持/读取失败直接解释为硬件损坏。
- 不仅凭单个事件或时间相关性断言根因。
- 引用设备 ID、Problem Code、事件 ID、时间戳和原始证据支持判断。
- 给出安全、可验证、按优先级排序的进一步检查建议。
- 明确指出软件无法测量或本次未采集到的关键项目。

## 9. 隐私、安全和操作边界

- 只读采集；不安装/更新/禁用/卸载驱动，不修改注册表、服务、系统配置或固件。
- 不执行压力测试、基准测试或自动修复。
- 不自动连接 AI、上传报告、同步云端或发送遥测。
- 导出前向用户说明可能包含的计算机名、用户名、序列号、设备 ID、路径、IP/MAC、事件消息等敏感内容，并允许预览/控制分享内容。
- 原始证据不得被静默删改；如提供脱敏副本，必须明确区分原始报告和用户选择的分享副本。
- 任何需要管理员权限的采集都必须提前解释并单独征得同意；普通采集优先以非管理员权限完成。

## 10. 明确的技术限制

软件不能保证获取硬件厂商未公开或未暴露的数据。典型限制包括：

- 主板未暴露的电压、温度、风扇或电流传感器。
- 未公开接口的厂商专有遥测。
- 需要外部仪器测量的电源纹波、瞬态响应、电气噪声和真实供电质量。
- 不能仅靠软件可靠验证的电源额定能力、线材/接头接触质量和物理损伤。
- 受控制器、驱动、固件或 RAID/USB 桥接限制而无法读取的 SMART/NVMe 细节。
- Windows 未保留、日志已覆盖、权限受限或设备已断开的历史信息。
- 无法仅凭一次快照证明的间歇性故障。

对上述项目必须给出“无法检测/本次不可获取”的解释及可能需要的外部工具或人工复核方式。报告不得宣称整机绝对健康或电气安全。

## 12. 验收方向（产品级）

完整产品达到目标时，应能够在用户明确确认后，对 Windows 当前可枚举设备进行广泛扫描；逐设备给出可追溯状态；汇总硬件、接口、驱动、传感器和系统可靠性证据；透明报告全部采集缺口；生成可人工检查、可供 AI 分析的 JSON/XLSX/HTML/AI 说明 ZIP 报告包。所有判断必须可追溯到数据来源和证据，不能将采集覆盖率或“正常”状态夸大为绝对硬件健康保证。
